# Gates: changing what a running service renders

Read `AGENTS.md` in this directory first; its "Presets are pinned" section is the problem this file answers. Read this file before you change anything that reaches a pod template, add a companion workload, or touch a limit that stored services already exceed.

Two questions run through every row below, in this order. Does everything that exists in clusters today keep working on the new version: that is compatibility, and it has no gate, it is simply required. Does the change disrupt what is running: that is what the gates are for. The table answers the second question; the first is answered by the stored-shape list. The answer is never "the shipped presets". It is the set of stored shapes: services pinned to each released preset, child objects the controller carries forward, and configs the controller's own earlier defaults and migrations wrote. A change is safe when every one of those shapes still renders, decodes and reconciles, or is migrated by code gated on the version that needs it. Build that list first, from previous releases, then pick the gate.

### The slot

The opt-in has to live in the preset, because the preset is what is pinned. A slot is a key a preset declares with a placeholder value. The controller fills it only where the merged spec carries it. A service on an older preset has no key, so its render stays byte-identical. The same mechanism lets a custom preset opt in by declaring the key.

Invariants:

- The controller never adds the key itself. It fills the value once, in one post-merge step, only where the key is present.
- The placeholder's value is checked, not only the key. Why: a value the user set must not be overwritten in silence.
- The key is stripped from every object it must not reach.
- Two services are rendered through the real reconciler, one pinned to a preset with the slot and one without; the second is byte-identical to today.
- The PR body and the release note name the slot, so custom presets know what to add.

The tree has four shapes of slot:

| Shape | Preset side | Controller side |
|---|---|---|
| empty env the preset script reads only when set | `KSERVE_KV_TRANSFER_ARGS` | `workload_kvcache.go:applyKVCacheCarriers` |
| version env the controller checks before it adds more output | `KSERVE_TRACING_CONFIG_VERSION` | `tracing.go:supportsComponentTracing` |
| placeholder label the controller replaces with a computed value | `serving.kserve.io/llmisvc-revision: placeholder` | `workload_revision.go` |
| a container the preset ships and the controller finds by name | the routing sidecar, an evictor | `workload.go:routingSidecar`; the companion row below |

## Operand flags are user input

The flags an EPP or sidecar container receives are not only what the shipped presets pass. A tenant copy of a preset, a `spec.router.scheduler.template` and an inline config all carry arbitrary args the controller renders as written, and `preserveSchedulerConfig` carries the running ones forward. When an operand release retires a flag, the binary rejects the whole argv and the pod crash-loops on the first reconcile after the bump, for every service that still passes it. The binary provider should keep a retired flag as a deprecated no-op for a release; when it does not, the controller owns the migration: detect the old flag in the rendered args and move its value to where the new version wants it (the five `--model-server-metrics-*` flags became `metrics-data-source` plugin parameters), gated on the pinned version, with a reason the tenant can act on when the move is impossible. Rewrite when every released image that passed the old flag accepts the new one; the pool-group rename qualified. Reject, with a terminal reason that names the replacement flag and the image floor that accepts it, only when a rewrite would itself break a released pin: the replacement for `--vllm-port` arrived in a later sidecar than one released preset pinned, and the scheduler annotation cannot tell which sidecar image a copy pins. Without the floor in the message, a tenant who changes only the flag on the old image gets `unknown flag`. The `Image CLI flag drift` workflow (`hack/verify-image-flag-drift.sh`) replays the flags our manifests, charts, samples and test fixtures pass against the bumped image's `--help`; it cannot see a tenant's template, which is why the controller migration exists and why a flag the check flags on a preset is a sign that user configs carry it too.

In the tree: `scheduler.go:extractDeprecatedMetricFlags`, `deprecatedMetricFlagNames`, `scheduler.go:filterArgs`, `config_merge.go:migrateLegacyPoolGroup`, `config_merge.go:validateRoutingSidecarArgs`, `.github/workflows/image-flag-drift.yml`.

## Which gate for which change

Behind every gating thread is one question: what happens to a service that already exists, on a cluster where only the controller changed. The gate follows from what the change touches. Name it in the PR body.

| You change | What must stay true | In the tree | Proof |
|---|---|---|---|
| a value in a pod template: env, arg, volume, label, annotation | only presets that declare the slot render it | the slot section above | envtest from the previous release's child object, `generation` unchanged |
| the same, keyed on the stored pod instead of a slot | every legitimate previous state of the stored pod renders unchanged. Why: a service that switched storage scheme looks like one created by an older controller | `workload_storage.go:attachStorageInitializer` adds `HF_*` env only when the current init container is new or already has one | generation-stable envtest with each previous state |
| output that depends on an operand version: router sidecar, EPP, vLLM, tokenizer | the version the merged spec pins decides, resolved in merge order (service, `baseRefs`, well-known preset) from the `app.kubernetes.io/version` annotation and compared as a version. Never the image tag, never the running pod. For vLLM, a `--help` probe in the preset. The tokenizer preset carries no version annotation today, and the decode presets carry none for the sidecar, so a sidecar decision keyed on the scheduler annotation cannot tell which sidecar image a copy pins; each needs its own key before anything gates on it | `config_merge.go:routerVersionSupportsPreset`, `scheduler.go:preserveSchedulerConfig`, the probe blocks in `config-llm-template.yaml` | a test pinned to the previous version |
| a migration or rename of an existing child: EPP plugin, flag | the old shape is detected on the current object and the expected version allows the new one. "No-op in theory" is not a gate | the pre-v0.7 renames in `scheduler.go`, `scheduler.go:filterArgs` | fixture from real previous-release output |
| an operand version bump that removes or renames config fields: EPP plugins and parameters, sidecar flags | every field the previous version accepted and the new one rejects is stripped or renamed in carried-forward configs by a migration gated on the new version. Take the list from the diff of the operand's types between the two tags, not from the release notes, which summarise: the config API under `apix/` and the plugin parameter structs under `pkg/` in llm-d-inference-scheduler, and the indexer config in llm-d-kv-cache (`pkg/kvcache/indexer.go`) that the precise-prefix plugins embed. The input set is every config the previous version accepted, not what this repo contains: a grep of presets, samples and kserve source for the field name proves nothing, because `migrateProducerParams` copies every `indexerConfig` key into the producer plugin and `preserveSchedulerConfig` carries any user config forward. Why: the EPP decodes its config with a strict serializer, so one leftover field stops the binary | `scheduler.go:schedulerTransform` version blocks, `migrateProducerParams` | a maximal config per plugin at the previous version, every parameter its types accepted populated, run through the migration chain and then loaded by the new EPP image; plus a `controller_int_scheduler_config_test.go` case from a real previous-version `--config-text`, run on the base and on the branch. Presets, samples and defaults alone are not a corpus: none of them carries the fields only user configs had |
| what clients or other controllers observe: routes, status fields, admission outcome, number of child objects | an `inferenceservice-config` key paired with a `serving.kserve.io/...` annotation decides, and the default equals today | `config_loader.go`, `router_lora.go` (`loraModelRoutingStrategy`) | master-vs-branch render of an unchanged service |
| an optional CRD or API group | one detection at startup, kept as a reconciler field; only genuinely optional groups are skipped, such as the v1alpha2 InferencePool; hard dependencies fail fast | `controller.go:SetupWithManager` | envtest without the CRD |
| a feature `enabled` flag | every reconciler of the feature honours it, and disabling has a defined effect on objects already created | `cmd/llmisvc/main.go`, `config_loader.go` | flip the flag in a test, assert no new objects |
| removal of a flag, field, plugin or template function | one release as a deprecated no-op with a Warning on actual use; the schema entry and the `templateFuncs` entry stay | the `flag.Visit` pattern, `config_merge.go:deprecatedTemplateFuncs` | a service that still carries the old input gets the warning |
| tighter validation | only creates and changed fields are rejected; stored objects keep updating. In llmisvc the rendered spec is dry-run created on every reconcile, so a ratchet keyed on the old object does not protect stored services: a tighter limit needs a compatibility path or stays out of the served versions | `self == oldSelf`, or unchanged-allowed in `pkg/apis/serving/v1alpha2/llm_inference_service_validation.go` | negative CEL test, an update of a stored object, and a regression test at the previous maximum |
| a companion workload beside or inside the consumer (evictor, permission fixer, sidecar) for a spec field that already exists | the pinned preset declares the companion: its container template with image, resources and security context. The controller renders, validates and reports the companion only where the merged spec carries that declaration. A service without it renders byte-identically and is never checked against the companion's rules | the slot section above; `scheduler.go` and `tokenizer.go` for the shape of a standalone helper | a legacy-preset envtest: the previous release's preset from `git show <tag>:config/llmisvcconfig/<preset>.yaml` as a namespace-local copy, a spec change applied, the change lands on the Deployment and the old preset's marker is still absent |

Answer a compatibility ask with a path that keeps the old render serving: skip the companion, warn, carry the value forward. Never with a tighter rejection applied to stored services. A rejection is the last resort, for an input no rewrite serves on every released pin, and it names the replacement and the image floor. A check over a list of modes rejects only when no acceptable mode is present. Why: in #6411 each compatibility fix became the next regression, a terminal error on every service from the previous release, three rounds in a row.

## Companion workloads and shared resources

A companion the controller adds for a spec field that already exists (a KV cache evictor for a PVC tier, a permission-fix Job for a mount, a sidecar, a tokenizer, a scheduler) reaches every running service with that field on the day the controller upgrades. Its defaults, the consumer-side changes that wire it (a label, a sidecar, a new cache root) and the checks that make it safe land at once, so a service on a preset that never heard of the companion either restarts or stops reconciling with a terminal error while its old pods keep serving. A companion shared by several services, one per namespace, claim and path, has no single owner: its template is the agreement of its consumers and its lifetime the union of their references. A companion that must run on the node of a consumer holding an exclusive resource follows an observed fact, where the consumer pod runs now.

Invariants, for companions the controller creates beside or inside a consumer workload:

- The preset declares the companion, including its container template, image, resources and security context. The controller never carries a companion default as a constant. Why: a digest bump or a downstream image override otherwise rolls every pod that has the field.
- A companion image the upstream build does not produce lives in the preset, and a distribution overrides it in its preset copy. If a ConfigMap key is unavoidable, the PR names the downstream companion change.
- A per-template override of the companion (worker, prefill, prefill worker) resolves through one fallback function that every builder calls.
- State derived from peers (template agreement, tolerations) is tracked per shared identity (claim plus path). A consumer that cannot be resolved degrades only the identities it references and only the fields that depend on it. A value computed from observed objects, such as the consumer's node, is written unconditionally. Why: one bad `baseRef` in the namespace must not freeze every other helper or leave one on the old node while the volume sits in Multi-Attach.
- Work for a shared companion scales with the consumers of its identity, found through a field index: agreement, cleanup and watch mappers select by index. A service with neither the feature nor managed companion objects does no peer merge, no live read and no dry-run.
- A change to a consumer's reference, through the spec or through a `baseRef` config, enqueues every consumer of that identity. The conflict test has two entries: the peer now agrees, and the peer drops the reference. Why: the drop case writes nothing, so without the enqueue the stuck peer waits for the resync.
- A name the controller reserves in user space (a container name, a label or annotation key) is documented in the field's godoc, rejected or ignored by the webhook on services without the feature, and stripped only where the feature renders it. Why: a user container with that name otherwise disappears in silence.
- A companion placed beside a consumer carries the consumer's tolerations and node selection. A standalone companion that is not placed beside a consumer gets a supported scheduling override instead; a reserved container template cannot carry pod-level fields.
- A co-located companion has a test that moves the consumer across three nodes and asserts the placement value written into the companion's pod template, with and without an unrelated broken peer. The write is the line a mutation deletes. Why: in #6411 deleting that write kept every unit and envtest spec green.
